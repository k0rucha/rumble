# アーキテクチャ

レビューするときに「どこに何があり、なぜそうなっているか」を追えるようにするための文書です。

## 全体像

```
┌──────────────────────────── フロントエンド (src/) ────────────────────────────┐
│  components/*.svelte   画面の部品。表示と入力だけ                              │
│          │                                                                    │
│  lib/store.svelte.ts   画面の状態と、利用者の操作 = アクション                 │
│          │                                                                    │
│  lib/backend.ts        Rust コマンドの呼び出し口 (コマンド名を知る唯一の場所)  │
└──────────┼────────────────────────────────────────────────────────────────────┘
           │ invoke / event
┌──────────┼──────────────── Tauri シェル (src-tauri/) ─────────────────────────┐
│  commands.rs           1 コマンド = MailService のメソッド 1 つ (丸投げ)       │
│  external_links.rs     メール内リンクを既定のブラウザへ回す                    │
└──────────┼────────────────────────────────────────────────────────────────────┘
           │
┌──────────┼──────────────── コア (crates/rumble-core/) ────────────────────────┐
│  service.rs            ユースケース層。外からはここだけを呼ぶ                  │
│     ├── imap/connection.rs   接続・再接続・タイムアウト                       │
│     ├── imap/ops.rs          IMAP 操作 (状態を持たない関数群)                 │
│     ├── imap/mapping.rs      サーバー応答 → domain 型                         │
│     ├── imap/watcher.rs      IDLE による受信トレイ監視                        │
│     ├── mime.rs              受信メールの解釈と HTML のサニタイズ             │
│     ├── smtp.rs              送信                                             │
│     ├── authenticity/        送信元の検証 (DKIM / DMARC / BIMI。DNS を引く)   │
│     ├── classifier.rs        自動分類 (外部の分類モデル Jev を呼ぶ)           │
│     ├── cache.rs             メモリ内キャッシュ (ディスクには書かない)        │
│     └── storage/             ディスクに触れる唯一の場所                       │
│  domain/               画面とやり取りするデータ型 (振る舞いなし)               │
└───────────────────────────────────────────────────────────────────────────────┘
```

依存は上から下への一方向です。`rumble-core` は Tauri を知らないので、GUI なしで
テストできます。

## 原則: メールをディスクに保存しない

rumble の存在理由です。コード上では次のように守っています。

- **コアのディスク書き込みは `storage/` に閉じ込める。** `AccountStore` (設定 JSON) と
  `SecretStore` (パスワード) の 2 つの trait がその全てで、どちらもメールを扱う
  メソッドを持ちません。パスワードの保管先はデスクトップでは OS のキーチェーン、
  資格情報ストアを使えない Android ではアプリ専用領域のファイル (`FileSecretStore`) です。
- **唯一の例外は添付ファイルの保存。** `src-tauri/src/commands.rs` の `save_attachment` が、
  利用者がダイアログで選んだ場所へ書き出します。コア (`MailService::attachment`) は
  中身を返すだけで、書き込みはしません。
- **キャッシュはメモリだけ。** `cache.rs` の `MessageCache` は開いたメールの生データを
  バイト数上限つき (64 MB) の LRU で保持します。永続化の手段を持ちません。
- **フロントエンドも保存しない。** `localStorage` などは使っていません。
  `store.svelte.ts` の状態は「いまサーバーから見えているものの写し」です。

「ローカル保存を足したくなったら `storage/` に trait を増やすことになる」ので、
原則を破る変更はレビューで必ず目に入ります。

## IMAP をどう使っているか

| やりたいこと | IMAP での実現 | 場所 |
|---|---|---|
| 一覧を少しずつ表示 | シーケンス番号の末尾から範囲 `FETCH`。取るのは `FLAGS` と一部ヘッダーだけ | `ops::list_messages` |
| 検索 | `UID SEARCH TEXT` (サーバー側で全文検索) | `ops::search_messages` |
| メールを開く | `UID FETCH BODY.PEEK[]` (PEEK なので勝手に既読にならない) | `ops::fetch_raw_message` |
| 既読・スター | `UID STORE ±FLAGS.SILENT` | `ops::set_flag` |
| 移動 | `UID MOVE`。非対応サーバーでは `COPY` + `\Deleted` + `EXPUNGE` | `ops::move_messages` |
| 削除 | ゴミ箱へ移動。ゴミ箱の中では完全削除 | `ops::delete_messages` |
| 送信済みの控え | `APPEND` (Gmail は自動保存するので省略) | `ops::append_message` |
| 新着の検知 | 専用接続で `IDLE` | `imap/watcher.rs` |
| 自動分類の結果を保存 | キーワードを `UID STORE +FLAGS.SILENT`。一覧の `FLAGS` と一緒に返ってくる | `ops::store_categories` |
| 区分で絞り込み | `UID SEARCH KEYWORD` | `ops::list_by_category` |
| フォルダの役割 | `LIST` の SPECIAL-USE 属性。無ければ名前から推測 | `imap/mapping.rs` |

### 状態を持たない操作

`ops.rs` の関数はどれも「セッションを受け取り、対象フォルダを `SELECT` し、コマンドを
発行して返す」だけです。「いま選択中のフォルダ」のような状態を関数の外に持たないので、
1 つの関数を読めばその操作の全てが分かります。メールの特定には、接続をまたいでも
変わらない UID だけを使います。

### 接続は 1 アカウントにつき 2 本

- **操作用** (`ImapConnection`) : 一覧・取得・フラグ変更など。`tokio::sync::Mutex` で
  直列化し、1 本の接続に 1 コマンドずつ流します。
- **監視用** (`InboxWatcher`) : 受信トレイを `IDLE` し続けます。IMAP では IDLE 中に
  他のコマンドを送れないため、操作用とは分けています。

`ImapConnection::run` が接続まわりの面倒を一手に引き受けます。

1. 未接続なら接続する
2. しばらく使っていなければ `NOOP` で生存確認し、だめならつなぎ直す (スリープ復帰対策)
3. 操作にタイムアウトをかける
4. 接続が壊れた種類のエラーならセッションを捨てる (次回つなぎ直す)

そのため `service.rs` や `ops.rs` には再接続のコードがありません。

### IDLE の通知は「変わった」だけ

監視側は通知の中身を解釈せず、「受信トレイが変わった」というイベントだけを
フロントエンドへ送ります。フロントエンドは通常の一覧取得をやり直します。
差分を自前で組み立てないので、表示がサーバーとずれる余地がありません。

## 送信元の検証

メールを開いたあと、本文の表示とは別に `MailService::verify_sender` を呼びます
(DNS を待つあいだ本文を待たせないため)。材料は 2 つあり、信頼の度合いが違うので混ぜません。

```
生データ (キャッシュ済み)
   ├─▶ authenticity/signature.rs   DKIM 署名を DNS の公開鍵で検算 ……… 自前の検算
   │                               + 差出人ドメインの DMARC 方針を取得
   ├─▶ authenticity/reported.rs    Authentication-Results を読む ……… サーバーの申告
   │
   ▼
authenticity/verdict.rs            2 つを 1 つの判定 (TrustLevel) にまとめる
   │
   ▼ 確認できた && DMARC が quarantine / reject のときだけ
authenticity/bimi.rs               ブランドロゴを DNS + HTTPS で取得
```

設計上の判断:

- **自前の検算を最優先にする。** 「確認済み (`Verified`)」になるのは、差出人ドメインの DKIM 署名を
  rumble 自身が検算して通ったときだけです。Authentication-Results は送信者にも書けるヘッダーで、
  受信サーバーが偽物を取り除いたかどうかを rumble からは確かめられません。そのため、サーバーの
  申告だけが根拠のときは別の段階 (`Reported`) にして、画面でも色と文言を変えています。
- **SPF は検算しない。** SPF は「どの IP から接続してきたか」の検査で、受信サーバーにしかできません。
  rumble が DMARC を評価するときは DKIM だけを材料にし、SPF はサーバーの申告として表示します。
- **いちばん上の Authentication-Results だけを読む。** ヘッダーは配送のたびに上へ積まれるので、
  いちばん上が自分のメールサーバーのものです。それより下は使いません。
- **判定の規則は 1 か所。** 合否の組み合わせから段階を決める規則は `verdict::judge` だけにあり、
  ネットワークに触れない純粋な関数なので、規則ごとに単体テストがあります。
- **ロゴは条件つき、かつ控えめに。** BIMI のロゴは「送信元を確認でき、ドメインが失敗メールの
  隔離・拒否を宣言している」場合だけ出します。証明書 (VMC) は検証していないので、画面では
  「ドメインが自分で公開しているロゴ」と説明し、認証済みマークのような見せ方はしません。
  メールごとのセレクター (BIMI-Selector ヘッダー) は無視して常に `default` を引きます
  (宛先ごとに違う名前を仕込んで開封を検知する、という使い方をさせないため)。
  ロゴは `<img>` で描くので、SVG 内のスクリプトは動きません。
- **ディスクには書かない。** DNS の応答 (`dns_cache.rs`) と取得したロゴはメモリに持つだけです。
- **DNS は平文の UDP/TCP。** OS に設定されたリゾルバーを使います。Android では OS の設定を読むのに
  追加の権限が要るため、Cloudflare の公開 DNS を直接使います。TLS つきの DNS にしなかったのは、
  そのための TLS ライブラリを Android 向けに追加でビルドする必要があるためです。

### ソース表示

`MailService::message_source` は、キャッシュ済みの生データをヘッダー部分と全体の 2 つの文字列に
して返すだけです (`mime::message_source`)。デコードも整形もしません。巨大なメールで画面が
固まらないよう、画面へ渡すのは先頭 1 MB までです。

## 自動分類

任意の機能で、TypeSafe の API キーを登録したときだけ動きます。

```
一覧を表示 ──▶ 区分の無いメールの UID を集める (store.svelte.ts #classifyUnsorted)
                  │
                  ▼
        MailService::classify_messages
          1. 手がかりのヘッダーだけを取得      ops::fetch_classification_signals
          2. Jev に 1 通 1 リクエストで尋ねる   classifier::Jev::classify_all
          3. 結果をキーワードとして保存        ops::store_categories
                  │
                  ▼
        次回からは一覧の FLAGS に区分が載ってくる (分類し直さない)
```

設計上の判断:

- **結果はサーバーに置く。** 区分は IMAP キーワード (`$rumble_<区分>`) としてメールに付けます。
  「メールに関する状態はサーバーが持つ」という原則のままで、分類結果のローカル DB を
  持たずに済み、端末間でも共有されます。キーワードを保存できないサーバーでは、
  起動中だけメモリに控えます (`MailService::remembered_categories`)。
- **本文は送らない。** モデルに渡すのは差出人・宛先・件名・一斉配信かどうかだけです
  (`classifier::MailSignals`)。一覧表示と同じくヘッダーの一部取得で済むので、分類のために
  本文を取得することも、外部へ本文を出すこともありません。
- **判断はモデル、方針はコード。** Jev は「どの区分か」と確からしさを返すだけで、
  確信度が低いときに「その他」とする、といった扱いは `classifier::decide` が決めます。
  「その他」も保存するのは、同じメールを何度も問い合わせないための「分類済み」の印だからです。
- **モデルを呼ぶ間は IMAP 接続を占有しない。** 取得 → 問い合わせ → 保存を別々の
  IMAP 操作に分けてあり、分類中もほかの操作が待たされません。

## フロントエンド

- **`backend.ts`** : `invoke` を呼ぶのはここだけ。Rust 側 `commands.rs` と 1 対 1。
- **`types.ts`** : `crates/rumble-core/src/domain` の型の写し (JSON は camelCase)。
- **`store.svelte.ts`** : 状態とアクションを持つ単一のストア。コンポーネントは
  ストアを読んで描画し、操作はストアのメソッドを呼ぶだけです。
- **楽観的更新** : 既読・スター・削除などは先に画面へ反映し、サーバーが拒否したら
  一覧を取り直してサーバーの状態に合わせます (正は常にサーバー)。
- **古い応答の破棄** : フォルダを素早く切り替えたとき、前のフォルダの応答で画面を
  上書きしないよう、リクエストに通し番号を振っています (`#listRequest` など)。

### 画面幅への対応

レイアウトの切り替えは CSS のメディアクエリ (760px) だけで行います。広い画面では
3 ペインを並べ、狭い画面 (スマートフォン) では一覧・本文を 1 画面ずつ見せ、フォルダ一覧は
引き出しにします (`App.svelte`)。デスクトップ用とモバイル用で部品を分けてはいません。
幅ではなく実行環境で決まる違い (モバイルではファイル添付を出さない、など) だけを
`lib/platform.ts` に置いています。

## HTML メールの安全対策

受信した HTML は信用できないので、三重に守っています。

1. **サニタイズ** (`mime::sanitize_html`) : スクリプト・フォーム・iframe などを除去。
2. **sandbox 付き iframe** (`HtmlBody.svelte`) : スクリプト実行を許可しない。
3. **CSP** : iframe 内から外部への通信を遮断。外部画像は利用者が「画像を読み込む」を
   押したときだけ許可します (開封確認用の画像対策)。

リンクのクリックは、iframe からウィンドウ全体への移動要求として届くので、
`external_links.rs` が横取りして既定のブラウザで開きます。外部のページが
アプリのウィンドウ内に読み込まれることはありません。

## 技術選定

| 対象 | 採用 | 理由 |
|---|---|---|
| UI | Svelte 5 + TypeScript | ランタイムが小さく、状態管理ライブラリなしで足りる |
| IMAP | `async-imap` | IDLE を含め非同期で扱える |
| メール解析 | `mail-parser` | ISO-2022-JP など日本語の古い文字コードまで面倒を見てくれる |
| 送信 | `lettre` | メール組み立てと SMTP を一手に担える |
| TLS | OS 標準 (`native-tls`) | バイナリが小さく、OS の証明書ストアをそのまま使える |
| HTML 無害化 | `ammonia` | ホワイトリスト方式 |
| 送信元の検証 | `mail-auth` | DKIM の検算と DMARC の評価を、暗号・DNS レコードの解釈ごと任せられる。暗号は純 Rust 実装を選び、Android 向けのビルドを増やさない |
| パスワード | `keyring` | 各 OS の資格情報ストアを共通 API で使える |

## テスト

- 自動分類は、リクエストの組み立てと応答の解釈を単体テストで、キーワードの保存と
  絞り込みを統合テストで確認しています。Jev の API を実際に呼ぶテストはありません
  (API キーが必要なため)。
- 送信元の検証は、試験用の鍵で署名したメールを実際に検算するテスト (合格・改ざん・別ドメイン) と、
  判定規則・Authentication-Results・BIMI レコードの解釈のテストがあります。DNS の応答は
  キャッシュに仕込むので、ネットワークには出ません。実際の DNS と HTTPS を使う確認は
  `cargo test -p rumble-core authenticity -- --ignored` です。
- **単体テスト** (`cargo test --workspace`) : ネットワークに触れない部分。
  MIME 解釈、サニタイズ、フォルダ名の変換、検索条件の組み立て、キャッシュ、
  送信メールの組み立て、設定ファイル、リンクの振り分け。
- **統合テスト** (`crates/rumble-core/tests/imap_server.rs`) : Docker の Dovecot に対して
  一覧・検索・フラグ・移動・削除・IDLE を実際に実行します。通常は `#[ignore]` です。
